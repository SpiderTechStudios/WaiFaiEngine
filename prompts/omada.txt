# TASK: Implement a Complete Multi-Tenant TP-Link Omada Integration in WaiFai

You are working on the existing WaiFai platform.

WaiFai is a paid Wi-Fi management platform built with:
- Laravel REST API backend.
- React frontend.
- Existing MikroTik integration.
- Existing Ruijie Reyee / WiFiDog integration.
- Payment integrations and captive portal functionality.

Your task is to implement a complete, production-ready **TP-Link Omada integration** that allows every WaiFai customer to connect their own Omada Controller and manage their Omada access points through WaiFai.

This must work as a reusable integration for multiple independent WaiFai customers.

## 1. CRITICAL: PROTECT EXISTING FUNCTIONALITY

Before writing or modifying code:

1. Inspect the entire existing project structure.
2. Identify the current MikroTik integration architecture.
3. Identify the current Ruijie / WiFiDog integration architecture.
4. Identify how customers currently register network devices.
5. Identify how router credentials, API connections, device records and authentication sessions are stored.
6. Identify the existing captive portal and payment-success authorization flow.
7. Identify existing database relationships and tenant isolation mechanisms.
8. Identify the existing frontend device registration forms and connection-testing patterns.

**DO NOT:**
- Delete, replace or rewrite existing MikroTik functionality.
- Delete, replace or rewrite existing Ruijie functionality.
- Change existing MikroTik API endpoints or connection logic unnecessarily.
- Change existing Ruijie WiFiDog endpoints or authentication logic.
- Rename existing database tables, fields, routes or services without a compelling compatibility reason.
- Change existing payment processing or package logic.
- Break existing customer device configurations.
- Introduce a new architecture that conflicts with established project conventions.

Implement Omada as an independent integration module.

Reuse existing abstractions and services where appropriate, but keep Omada-specific functionality isolated.

All database changes must be additive migrations.

Before modifying shared code, explain why the change is necessary and how backward compatibility will be preserved.

## 2. OBJECTIVE

A WaiFai customer should be able to:

1. Open their WaiFai dashboard.
2. Navigate to Network Devices.
3. Select Add Device.
4. Select TP-Link Omada.
5. Choose their Omada Controller deployment type.
6. Enter the required controller connection information.
7. Test the connection.
8. Retrieve available Omada sites.
9. Select the site they want to connect.
10. Discover the access points belonging to that site.
11. Configure their SSID and external captive portal.
12. Save the integration.
13. Start accepting customers through the WaiFai captive portal.

A customer must never see or access another WaiFai customer's Omada controllers, sites, credentials, devices or client sessions.

## 3. SUPPORT ALL THREE OMADA DEPLOYMENT TYPES

The integration must support:

### A. Omada Software Controller
- Windows installation.
- Linux installation.
- Self-hosted installations.
- Custom controller domains and IP addresses.
- Custom management/API ports.
- HTTPS certificates, including properly configured private or self-signed certificate environments where appropriate.

### B. Omada Hardware Controller
- OC200.
- OC300.
- Other supported Omada hardware controller models.

### C. Omada Cloud Controller
- Cloud-hosted Omada deployments.
- Officially supported cloud API and authentication mechanisms.
- Any required cloud account, controller ID, site ID or API credentials.

Do not assume that all three deployment types use the same API endpoints, authentication methods or network requirements.

Research and follow the official TP-Link Omada API documentation for each supported controller version and deployment type.

If a deployment type or controller version does not support the required external portal authorization functionality, clearly identify the limitation rather than pretending that it works.

## 6. NETWORK CONNECTIVITY ARCHITECTURE

This is particularly important.

Omada controllers can be located:
- On the customer's local network.
- Behind NAT.
- On a public IP.
- On a customer-managed cloud environment.

A private address such as 192.168.x.x cannot be reached directly from the WaiFai VPS.

Design the integration to support appropriate secure connection methods, including:

- Public HTTPS controller endpoints.
- Secure VPN/WireGuard connectivity.
- Supported cloud-controller API access.
- Other officially supported secure connectivity mechanisms.

Do not require every customer to expose their controller directly to the public internet.

Do not hardcode any test controller address or credentials.

If a secure tunnel or customer-side agent is necessary, design it as an optional, independently managed connectivity component.

## 7. OMADA EXTERNAL CAPTIVE PORTAL INTEGRATION

The goal is for Omada customers to use the existing WaiFai captive portal.

Expected flow:

1. A user connects to the customer's Omada SSID.
2. Omada redirects the user to the WaiFai external captive portal.
3. WaiFai receives the Omada client information.
4. WaiFai displays the existing package selection and payment interface.
5. The user selects a package.
6. The user completes payment through the existing WaiFai payment system.
7. WaiFai verifies payment through the existing payment verification mechanism.
8. WaiFai authorizes the client through the correct Omada Controller API.
9. Omada grants internet access.
10. The customer receives access according to the purchased package duration.

### External portal parameters

Implement handling for the actual parameters supplied by Omada, including where available:

- clientMac
- clientIp
- apMac
- ssidName
- site
- redirectUrl
- radioId
- timestamp parameter `t`

Preserve the original Omada parameters throughout the package selection and payment process.

Do not rely only on IP address to identify a client.

Use the appropriate combination of:
- Client MAC.
- Client IP.
- AP MAC.
- Site ID.
- SSID/WLAN.
- Controller identity.

Validate all incoming parameters.

Do not trust client-submitted information as proof of successful payment or authorization.

### Captive portal URL

Generate the correct WaiFai captive portal URL for each customer and their configured network.

Follow the existing WaiFai portal routing and subdomain architecture.

Do not create a separate payment interface for Omada.

Reuse the existing WaiFai captive portal and payment flow.

## 8. OMADA CLIENT AUTHORIZATION

Implement a dedicated Omada authorization service.

After verified payment, the Laravel backend must communicate with the correct customer's Omada Controller and authorize the client.

Follow the official API documentation for the specific controller version and deployment type.

Implement:
- Controller authentication.
- API session/token handling.
- Client authorization.
- Access duration.
- Authorization response validation.
- Session tracking.
- Client disconnection/deauthorization.
- Reconnection handling.
- API token/session refresh where necessary.

Do not assume the API endpoints are identical across controller generations.

Do not hardcode API endpoints based on an old Omada example.

### Duration handling

Map WaiFai package durations to the actual authorization duration supported by the controller API.

For example:
- 30 minutes.
- 1 hour.
- 3 hours.
- 12 hours.
- 24 hours.
- Custom package duration.

If the controller requires a different duration format, convert it correctly.

### Payment security

Only authorize a device after successful payment verification.

Prevent:
- Double authorization caused by repeated payment callbacks.
- Duplicate sessions.
- Unauthorized access caused by forged portal requests.
- Reusing another customer's payment or authorization data.

Authorization must be idempotent.

If payment succeeds but the controller is temporarily unavailable, retain the verified payment state and implement a safe retry mechanism.

Never mark the client as successfully authorized until the controller confirms authorization.

- Prevent access to localhost, private infrastructure and cloud metadata endpoints unless explicitly required by a properly configured private-network connection.
- Protect against cross-tenant access.
- Use authorization policies and middleware.
- Validate all external portal requests.
- Use secure token/session management.
- Implement appropriate request timeouts and rate limiting.
- Do not disable TLS certificate verification in production.
- Do not allow customers to use another customer's controller credentials.
