# TASK: Add TP-Link Omada to the WaiFai dashboard

You are working on the WaiFai frontend (React or equivalent SPA) that consumes the
WaiFai Laravel API.

Implement TP-Link Omada as a new **Network Device** type alongside MikroTik and
Ruijie. Do not change the existing MikroTik or Ruijie registration screens except
for adding Omada as a selectable option.

The Omada backend module is already implemented. This task is frontend only.

---

## 1. Environment

```
VITE_API_BASE_URL=https://api.waifai.co.tz/api/v1
VITE_OMADA_ENABLED=true
```

- Do not put any Omada controller credentials in frontend environment variables.
  Every customer enters their own controller credentials; the backend stores them
  encrypted.
- Do not expose `client_secret`, `operator_password`, or any token in the UI,
  logs, analytics, or error reports.

## 2. Auth and permissions

All tenant endpoints use the existing auth/company context:

```
Authorization: Bearer {sanctum_token}
Accept: application/json
```

Reuse the existing router permissions:

| Action | Permission |
| --- | --- |
| List/view/test/status | `routers.view` |
| Create integration | `routers.create` |
| Update, select site/AP/SSID, disconnect | `routers.update` |
| Sync | `routers.sync` |
| Delete | `routers.delete` |

## 3. Response envelope

Every endpoint returns:

```json
{
  "status": true,
  "code": 200,
  "message": "Success",
  "data": {}
}
```

Errors use the same envelope with `status: false`:

```json
{
  "status": false,
  "code": 422,
  "message": "Validation Error",
  "data": { "field": ["message"] }
}
```

Handle:

| Code | Meaning |
| --- | --- |
| 401 | Not authenticated |
| 403 | Missing permission / inactive company |
| 404 | Not found or another tenant's integration |
| 422 | Validation error; render `data` field errors |
| 429 | Rate limited; honour `retry_after` seconds |
| 502 | Omada controller/API failure; show `message` |

A connection test that fails authentication usually returns **HTTP 200** with
`data.authenticated = false` and a `message`. Do not treat that as a transport
error.

## 5. Wizard steps

### Step 1 — Controller deployment type

Required: `deployment_type`

| Value | Label |
| --- | --- |
| `software` | Software Controller (Windows/Linux/self-hosted) |
| `hardware` | Hardware Controller (OC200 / OC300) |
| `cloud` | Cloud Controller |

Only show fields relevant to the selected type.

### Step 2 — Controller connection

Required for create:

- `name` — integration/device name
- `controller_url` — controller management URL or hostname
- `client_id` — Omada Open API Client ID
- `client_secret` — Omada Open API Client Secret
- `operator_username` — Omada Hotspot Operator username
- `operator_password` — Omada Hotspot Operator password

Optional:

- `controller_port` — defaults to 8043 (software) or 443 (hardware); allow override
- `controller_id` — Omada Controller ID / `omadacId`; can be discovered
- `connection_method` — `public` (default), `vpn`, `cloud`
- `verify_tls` — boolean, default `true`
- `branch_id` — optional existing branch/station id

Rules to show in helper text:

- Use HTTPS. HTTP is only allowed when the platform explicitly enables it.
- Private addresses (192.168.x, 10.x, 172.16–31.x, localhost) are rejected unless
  `connection_method` is `vpn` and the platform allows private hosts.
- Disabling TLS verification is rejected unless the platform allows self-signed
  certificates. Prefer uploading a trusted certificate to the controller.
- How to get Client ID/Secret: Omada Global view → Settings → Platform Integration
  → Open API → Add New App → Client Credentials mode.
- How to get the Hotspot Operator: Omada Hotspot Manager → Operator → Add New
  Operator. This is not the controller admin account.

## 8. Captive portal and payment wiring (important)

Omada redirects the client browser to:

```
GET /api/omada/portal/{portalKey}?clientMac=...&clientIp=...&apMac=...&ssidName=...&site=...&radioId=...&redirectUrl=...&t=...
```

The backend validates the parameters, creates/reuses an `OmadaClientSession`, and
returns:

```json
{
  "integration": { "id": 1, "name": "Omada HQ", "deployment_type": "software", "site_id": "site-1", "site_name": "HQ" },
  "client": { "mac": "AA-BB-CC-DD-EE-FF", "ip": "10.0.0.20", "ap_mac": "AA-BB-CC-DD-EE-01", "ssid": "WaiFai Guest" },
  "client_session_id": 15,
  "authorization_status": "pending",
  "portal_url": "https://api.../connect?subdomain=omada-cafe",
  "authorize_url": "https://api.../api/omada/portal/{portalKey}/authorize"
}
```

After the existing WaiFai payment flow reports the transaction as `paid`, call:

```
POST /api/omada/portal/{portalKey}/authorize
{ "client_session_id": 15, "payment_transaction_id": 900 }
```

or, when an access grant/voucher is used:

```
POST /api/omada/portal/{portalKey}/authorize
{ "client_session_id": 15, "access_grant_id": 44 }
```

Rules:

- Authorization must be idempotent; do not call it repeatedly from polling loops.
- Never send `clientMac`, `site`, or `ssidName` as proof of payment.
- Only a backend-verified `paid` transaction or a valid active grant authorizes.
- If the controller is temporarily unavailable, keep the paid state and retry.
- Never show "connected" until the authorize response says `authorization_status: authorized`.

**Current limitation:** the shared `/connect` portal and `PaymentService` do not
call the Omada authorize endpoint yet. Until that backend hook is added, the
frontend must perform this call after verified payment, or the integration must be
considered "authorization not wired". Do not fake success in the UI.

## 9. Integration object fields

```ts
interface OmadaIntegration {
  id: number;
  name: string;
  deployment_type: 'software' | 'hardware' | 'cloud';
  controller_url: string;
  controller_host: string;
  controller_port: number;
  controller_id: string | null;
  controller_version: string | null;
  connection_method: 'public' | 'vpn' | 'cloud';
  verify_tls: boolean;
  site_id: string | null;
  site_name: string | null;
  site_timezone: string | null;
  connection_status: 'connected' | 'unreachable' | 'unauthorized' | 'misconfigured' | 'unknown';
  status: 'active' | 'inactive';
  last_connected_at: string | null;
  last_synced_at: string | null;
  credentials_set: {
    client_id: boolean;
    client_secret: boolean;
    operator_username: boolean;
    operator_password: boolean;
  };
  portal_url: string | null;
  router_id: number | null;
  sites_count?: number;
  access_points_count?: number;
  ssids_count?: number;
  active_clients_count?: number;
  created_at: string;
  updated_at: string;
}
```

`credentials_set` is the only credential information the API returns.

## 10. Error and UX copy

Use clear, non-technical messages:
