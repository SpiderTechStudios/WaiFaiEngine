==============================================================================
WaiFaiEngine - Making MikroTik Work End-to-End (connect -> pay -> internet)
==============================================================================
Companion to : mikrotik.txt (current-build assessment)
Date         : 2026-11-02
Goal         : MikroTik clients get the same experience Ruijie clients get:
               connect -> captive portal opens automatically -> pay/voucher
               -> internet opens -> session is tracked -> user can be removed.

This document is an implementation plan, not a claim that the features exist.
Everything under "CURRENT" is already in the code; everything under "ADD" is
what you must build.

------------------------------------------------------------------------------
0. THE HONEST SUMMARY
------------------------------------------------------------------------------
Ruijie works because the access point speaks WiFiDog:

  browser -> backend portal -> payment -> backend marks session authenticated
  -> backend gives browser http://{gw}:{port}/wifidog/auth?token=...
  -> AP calls backend /api/wifidog/auth -> "Auth:1" -> AP opens internet.

MikroTik does NOT speak WiFiDog. It will never call /api/wifidog/auth.
So you cannot "just add mikrotik to GatewayResolver". You need the MikroTik
equivalent of the last leg:

  backend -> RouterOS REST API -> create a one-time hotspot user (or RADIUS
  account) with the purchased limits
  -> browser is sent to a backend page that auto-submits that user/password
     to the router's own hotspot login endpoint
  -> router authenticates locally -> client appears in /ip hotspot active
  -> internet works.

That is the closest possible equivalent to the Ruijie flow, and it reuses the
REST channel you already use for reboot. The rest of the plan below turns that
into a production feature.

Decision to make up front:
  Option A (recommended for phase 1): RouterOS REST + one-time hotspot user +
      browser auto-login. No new infrastructure. Works with the current
      Laravel app and the existing encrypted router credentials.
  Option B (recommended for scale / true accounting): RADIUS. Run FreeRADIUS
      (or a managed RADIUS) and point MikroTik at it. More infrastructure and
      more setup, but it is the standard carrier-grade way and gives real
      accounting + disconnect messages.

Do A first. Keep B as the migration path when you have many routers or need
accurate accounting. Details for both are below.

1. WHAT "SAME AS RUIJIE" MEANS - STEP MAPPING
------------------------------------------------------------------------------
+------------------------------+---------------------------------------------+
| Ruijie / WiFiDog step        | MikroTik equivalent you must build          |
+------------------------------+---------------------------------------------+
| AP redirects unauthenticated | login.html on the router redirects the      |
| client to login              | browser to the backend portal               |
|                              |                                             |
| GET /api/wifidog/login       | GET /api/mikrotik/login                     |
| creates pending session      | same, keyed by router id + portal key       |
|                              |                                             |
| backend -> /connect portal   | same /connect portal (no change)            |
|                              |                                             |
| payment / voucher / offer    | same payment/voucher/offer code (no change) |
|                              |                                             |
| backend marks session        | same CaptiveSession authenticate (no       |
| authenticated                | change)                                     |
|                              |                                             |
| backend returns              | backend returns /gateway/mikrotik/{token}   |
| http://gw/wifidog/auth?token | which auto-submits username/password to     |
|                              | http://{router-lan}/login                   |
|                              |                                             |
| AP calls /api/wifidog/auth   | RouterOS authenticates the one-time user    |
| -> "Auth:1"                  | locally; no server-to-server auth needed    |
|                              |                                             |
| AP opens internet            | router adds client to /ip hotspot active    |
|                              |                                             |
| AP sends /ping heartbeat     | backend polls /rest/system/resource and     |
|                              | /rest/ip/hotspot/active (or router callback)|
|                              |                                             |
| AP sends counter/usage       | backend reads bytes-in/bytes-out from       |
|                              | /rest/ip/hotspot/active                     |
|                              |                                             |
| AP sends logout              | router on-logout callback (optional) or     |
|                              | backend poll marks session ended            |
|                              |                                             |
| backend tells AP to remove   | backend calls /rest/ip/hotspot/active/remove|
| (not implemented for Ruijie) | and /rest/ip/hotspot/user/remove            |
+------------------------------+---------------------------------------------+

Key architectural difference:
  Ruijie: gateway pulls the decision from the backend (pull).
  MikroTik: backend pushes the entitlement to the router (push) + browser
            logs in. Both achieve "pay -> internet", but the direction flips.

3. WHY NOT OTHER SHORTCUTS
------------------------------------------------------------------------------
3.1 Do NOT try to make MikroTik call /api/wifidog/auth
    MikroTik has no WiFiDog auth-server client. There is no supported setting
    for "external WiFiDog server". Only custom scripts could emulate it, and
    you would still need the router to enforce the decision. Rejected.

3.2 Do NOT use ip-binding type=bypassed as the primary mechanism
    /ip hotspot ip-binding add mac-address=AA:... type=bypassed
    does grant access, but:
      - no hotspot user, no profile, no rate limit, no uptime limit
      - no per-session accounting in /ip hotspot active
      - the binding survives until explicitly removed; if your backend is down,
        the client keeps access forever
      - no clean "logout" or "expire" on the router
    It is useful as an emergency bypass, not as the product flow.

3.3 Do NOT call RouterOS REST from inside a DB transaction
    PaymentService::markPortalPaid currently runs in DB::transaction and calls
    authorizeCaptiveIfPresent inside it. Adding a 5-10s router call there will
    hold row locks and can time out the webhook. Provision lazily when the
    gateway page is opened, or queue a job with DB::afterCommit. This plan
    uses lazy provisioning + an optional queued job.

3.4 Do NOT reuse GatewayResolver as-is
    GatewayResolver::supportsWiFiDog requires a gateway_id/serial and either
    Ruijie/Wavlink or a wifidog_port. A normal MikroTik record fails this.
    Add a separate MikroTik resolver instead of weakening the WiFiDog gate.

4. ROUTEROS PREREQUISITES
------------------------------------------------------------------------------
4.1 Version and services
    - RouterOS v7.x is required for the REST API. v6 needs the legacy API or
      SSH; this plan targets v7.
    - Enable the REST service on the WAN side:
        /ip service set www-ssl disabled=no port=443 certificate=<cert>
      or, less securely, port 80:
        /ip service set www disabled=no port=80
    - The backend reaches {scheme}://{api_host}:{api_port}/rest/...
      The scheme is https unless the port is 80 (current code behavior).

4.2 Dedicated API user (do not reuse the hotspot admin)
    /user group add name=waifai-rest policy=read,write,api,rest-api,test
    /user add name=waifai-rest group=waifai-rest password=<strong> \
        address=<backend-egress-ip>/32
    Notes:
      - Policy names vary slightly by RouterOS 7 minor version. If
        "rest-api" is rejected, use read,write,api.
      - The address restriction is essential if the API is exposed publicly.
      - Do not give this user policy=policy or full; it only needs hotspot
        user/profile/active and system resource.

4.3 Hotspot
    /ip hotspot setup
    # choose the LAN bridge that serves clients
    # choose the hotspot profile (default is fine initially)
    # choose a DNS name and addresses

    Ensure HTTP PAP is enabled so the auto-login form can post a plaintext
    password over the LAN:
      /ip hotspot profile set [find name=<profile>] login-by=http-pap
    If you also want the router's own login page to work, use:
      /ip hotspot profile set [find name=<profile>] \
          login-by=http-chap,http-pap
    Avoid login-by=https for the first version; it adds certificate steps and
    the auto-login form would need to post to https.

4.4 Walled garden (critical)
    The client must reach the backend before it is authenticated:
      /ip hotspot walled-garden add dst-host=<backend-host> action=allow \
          comment="WaiFai portal"
      /ip hotspot walled-garden ip add action=accept \
          dst-address=<backend-ip> comment="WaiFai portal"
    Add the same for any payment provider page that the browser must open
    (PalmPay checkout, Flutterwave, etc.). PalmPesa USSD normally does not
    need a browser redirect.
    Also allow the backend's CDN/asset host if assets are on another domain.

4.5 Hotspot HTML directory - it is more than login.html
    RouterOS serves a small "servlet" from the hotspot html-directory
    (default path: hotspot/):

      /login     -> login.html
      /logout    -> logout.html
      /status    -> status.html
      /redirect  -> redirect.html
      /error     -> error.html
      /alogin    -> alogin.html
      /radvert   -> radvert.html   (only when hotspot advertise=yes)

    Plus md5.js, img/ and xml/ assets.

    Only login.html is strictly required to reach the external portal.
    The other files are still served and decide what the user sees after
    login, after logout, when already logged in, and on errors. For a
    production flow, treat them as part of the integration:

    +---------------+------------------------------------------+-------------+
    | File          | When RouterOS serves it                  | Action      |
    +---------------+------------------------------------------+-------------+
    | login.html    | before auth, and /login                  | REQUIRED    |
    |               |                                          | redirect to |
    |               |                                          | the backend |
    | redirect.html | after a successful /login when dst is    | Optional    |
    |               | present; sends browser to original URL   | neutral     |
    |               |                                          | "connected" |
    | status.html   | /status while authenticated; also used   | Optional    |
    |               | for "already online" and logout views    | brand +     |
    |               |                                          | link back   |
    | logout.html   | after /logout                            | Recommended |
    |               |                                          | redirect to |
    |               |                                          | portal      |
    | alogin.html   | /login while already authenticated       | Recommended |
    |               |                                          | redirect to |
    |               |                                          | status or   |
    |               |                                          | portal      |
    | error.html    | login error / expired / rejected         | Recommended |
    |               |                                          | friendly +  |
    |               |                                          | portal link |
    | radvert.html  | only when hotspot advertise=yes          | Leave or    |
    |               |                                          | disable     |
    | md5.js        | CHAP login helper                        | Keep        |
    | img/, xml/    | assets / WISPr                           | Keep        |
    +---------------+------------------------------------------+-------------+

    Why each non-login page matters:

    redirect.html
      The auto-login page posts dst=<original URL>. When dst is present,
      RouterOS normally redirects there. If dst is empty, the default
      redirect/status page may show a blank RouterOS page. Always send dst
      (fallback to http://www.google.com).

    alogin.html
      A returning device with a valid grant may already be authenticated on
      the router. If it opens the hotspot URL, RouterOS can serve alogin.html
      instead of login.html. Do not leave it as a dead-end: send the user to
      /status, the original URL, or the portal. Without this, a returning
      user can get stuck on "already logged in" and never see the portal.

    status.html
      This is the page behind /status and the normal "you are online" view.
      It carries the logout control and session counters. If you brand
      anything, brand this one too, and keep a "Buy another package" or
      "Back to portal" link.

    logout.html
      Served after /logout. Send the user back to the portal (or show a clear
      "logged out, buy again" page), otherwise they land on a bare RouterOS
      page. The backend session is marked ended by the on-logout callback or
      the sync poll; the HTML page itself does not notify the backend.

    error.html
      The auto-login can fail: user removed, grant expired, profile missing,
      router config reset. Without a friendly error page, the user sees a
      RouterOS error string and has no route back to payment/support. Show
      $(error) plus a link to the portal.

    radvert.html, md5.js, img/, xml/
      radvert only matters if hotspot advertising is enabled (leave it off).
      md5.js is needed only for HTTP CHAP; keep it even if you use HTTP PAP.
      img/ and xml/ are assets/WISPr support; keep them.

    Back up the whole directory before changing anything:
      /file copy hotspot/login.html hotspot/login.html.bak
      /file copy hotspot/status.html hotspot/status.html.bak
      /file copy hotspot/logout.html hotspot/logout.html.bak
      /file copy hotspot/redirect.html hotspot/redirect.html.bak
      /file copy hotspot/alogin.html hotspot/alogin.html.bak
      /file copy hotspot/error.html hotspot/error.html.bak
    If the hotspot profile uses a custom html-directory, use that path
    instead of hotspot/.

    Minimum viable set for phase 1: login.html only.
    Production set: login.html + logout.html + alogin.html + error.html,
    with status.html/redirect.html checked for branding/dead ends.

4.6 Reachability (choose one)
    A) Public IP / DDNS + port forward
       - Forward WAN 443 -> router 443 (or a non-standard port).
       - Save the public host in api_host and the port in api_port.
       - Firewall:
           /ip firewall filter add chain=input protocol=tcp dst-port=443 \
               src-address=<backend-ip> action=accept place-before=0
           /ip firewall filter add chain=input protocol=tcp dst-port=443 \
               action=drop
       - This exposes RouterOS to the Internet. The user address restriction
         and firewall allowlist are mandatory.
    B) WireGuard / VPN (recommended)
       - Router is a WireGuard peer; backend connects to its VPN address.
       - Set connection_mode=vpn and allow a private api_host for that router
         (the current validation rejects private hosts; add an exception).
       - No public RouterOS management port.
    The backend must be able to initiate REST calls to the router. If it
    cannot, payment-time provisioning is impossible. Do not start Option A
    without this.

4.7 Clock and DNS
    /system ntp client set enabled=yes servers=pool.ntp.org
    /ip dns set servers=1.1.1.1,8.8.8.8 allow-remote-requests=yes
    Correct time matters for TLS, limits, and comment/expiry comparisons.

5. BACKEND ENDPOINTS TO ADD
------------------------------------------------------------------------------
5.1 GET /api/mikrotik/login  (browser, no auth, throttle 120/min)
    Called by hotspot/login.html.

    Query:
      router=<network_device_id>   required
      key=<portal_key>             required
      mac=AA:BB:CC:DD:EE:FF        required
      ip=192.168.88.50             optional
      url=http://example.com       optional (original destination)
      subdomain=<company>          optional (validated if present)

    Behavior:
      1. Load NetworkDevice by id.
      2. Require type=router, gateway_type=mikrotik, status=active.
      3. Require company active and subdomain matches (or use company's).
      4. hash_equals(router->portal_key, key).
      5. Normalize MAC; reject invalid.
      6. update last_seen_at = now().
      7. captiveSessionService->resolveOrCreate(router, [
           ip, mac, ssid, url,
           gw_address => router->lan_ip,
           gw_port    => router->hotspot_port ?: 80,
         ]).
      8. 302 to captiveSessionService->portalRedirectUrl($session).

    Errors:
      404 unknown/inactive router or company
      403 bad portal key
      422 invalid MAC

    Security:
      - This endpoint is spoofable (like /api/wifidog/login). The portal key
        only scopes the router; the payment step is the real authorization.
      - Throttle per IP and cap pending sessions per router.
      - Do not trust a client-supplied gw_address; use the stored lan_ip.

5.2 GET /gateway/mikrotik/{token}  (browser, no auth, throttle 60/min)
    Returns HTML, not JSON. This is the replacement for the WiFiDog auth URL.

    Behavior:
      1. Load CaptiveSession by token, with company/router/grant.
      2. 404 if missing; 410 if expired; 302 to /connect if not authenticated.
      3. Ensure the grant is usable.
      4. ensureProvisioned(session) via MikroTikService.
      5. If the router's active list already contains this MAC, redirect to
         the requested URL (or show "you are already online").
      6. Render an auto-submit form to:
           http://{gw_address}:{gw_port}/login
         fields:
           username = session->mikrotik_username
           password = decrypted session->mikrotik_password
           dst      = safe requested_url or http://www.google.com
           popup    = 1
      7. Include a visible "Continue" button as a fallback if JS is blocked,
         and a link to the portal on failure.
      8. Headers: Cache-Control: no-store, X-Robots-Tag: noindex.

    Do not provision inside PortalPaymentResource serialization. This page is
    the only place that should make the provisioning call.

5.3 POST /api/mikrotik/callback  (router -> backend, optional but recommended)
    Requires X-MikroTik-Secret (or ?secret=) equal to the per-router
    callback_secret. Throttle 120/min.

    Body (JSON or form):
      {
        "router": 12,
        "event": "login" | "logout" | "accounting",
        "user": "wf_<token>",
        "mac": "AA:BB:CC:DD:EE:FF",
        "address": "192.168.88.50",
        "bytes_in": 12345,
        "bytes_out": 67890,
        "uptime": "1h2m3s",
        "session_id": "*1A"
      }

    Effects:
      login      -> set router_authorized_at/router_active_id on the captive
                    session; ensure NetworkSession started_at is set
      accounting -> update upload/download/last_activity
      logout     -> update usage; end the NetworkSession; mark captive session
                    disconnected if no other active session remains

    Always return 204 on accepted events. Return 401 for bad secret, 404 for
    unknown router, 422 for bad payload. Do not let a callback failure break
    the router; the sync job is the reconciliation path.

5.4 GET /api/mikrotik/ping  (router -> backend, optional)
    For NAT/firewall setups where the backend cannot poll the router.
    Query: router, secret. Updates last_seen_at. Returns "Pong" text/plain.
    Only needed if you choose router-initiated heartbeat over backend polling.

5.5 Admin client APIs (auth required)
    GET    /api/v1/routers/{router}/clients
    DELETE /api/v1/routers/{router}/clients/{mac}

    Permissions:
      GET    routers.view
      DELETE routers.update (or a new routers.clients.manage)

    GET maps /rest/ip/hotspot/active into:
      [
        {
          "id": "*1A",
          "user": "wf_<token>",
          "mac": "AA:BB:CC:DD:EE:FF",
          "ip": "192.168.88.50",
          "uptime": "1h2m3s",
          "bytes_in": 12345,
          "bytes_out": 67890,
          "comment": "wf|1|123|2026-11-02T12:00:00Z",
          "captive_session_id": 123,
          "network_session_id": 456
        }
      ]

    DELETE removes the active entry, the hotspot user, and the cookie, then
    updates the local DB records. Idempotent: removing a MAC that is already
    gone returns success with removed=0.

5.6 Router management changes
    POST /api/v1/routers/{router}/test
      For MikroTik, replace the TCP-only check with:
        GET /rest/system/resource
        GET /rest/ip/hotspot/active
      Return:
        reachable, authenticated (true when GET succeeds),
        routeros_version, uptime, active_clients, hotspot_enabled,
        latency_ms, message
      Keep the TCP fallback behind a config flag for old routers.

    GET /api/v1/routers/{router}/setup
      Rewrite the MikroTik steps (current guide has invalid commands):
        1. Enable REST + create API user + firewall allowlist.
        2. Run /ip hotspot setup.
        3. Add walled garden host + IP.
        4. Install login.html (return the exact content + a fetch command).
        5. Set login-by=http-pap.
        6. Return portal URL, router id, portal key.
        7. Tell the operator to run "Test connection" and verify REST.
      Do NOT emit dst-address=<hostname>. Use dst-host for names, or resolve
      the IP and use dst-address=<ip>.

6. SERVICES AND CODE CHANGES
------------------------------------------------------------------------------
6.1 New: app/Services/MikroTik/MikroTikService.php
    A thin RouterOS REST client plus hotspot operations. Suggested shape:

      class MikroTikService
      {
          public function test(NetworkDevice $router): array;
          public function ensureProvisioned(CaptiveSession $session): void;
          public function revoke(CaptiveSession $session): void;
          public function removeByMac(NetworkDevice $router, string $mac): array;
          public function activeClients(NetworkDevice $router): array;
          public function syncRouter(NetworkDevice $router): void;
          public function ensureProfile(NetworkDevice $router, InternetPlan $plan): string;
      }

    HTTP wrapper:
      - base URL: {scheme}://{api_host}:{api_port}/rest
      - scheme: https unless port 80
      - Basic auth: api_username / decrypted api_password
      - timeout: 5s connect / 10s total
      - Accept: application/json
      - TLS verification: configurable (api_verify_tls, default true)
      - no retry on POST mutations; retry GET once on connection failure
      - log method, path, status, router id, duration; NEVER log the password,
        Authorization header, or hotspot user password.

    Error type:
      class MikroTikException extends RuntimeException
      with a user-safe message and a context array (router id, path, status).

6.2 Gateway resolution
    Add GatewayResolver::resolveMikroTik(int $id, string $key): NetworkDevice
    (or a separate MikroTikGatewayResolver). Checks:
      - type=router, gateway_type=mikrotik
      - status=active
      - company active + subdomain present
      - hash_equals(portal_key, key)
    Do not change supportsWiFiDog(); it must keep rejecting plain MikroTik.

6.3 CaptiveSessionService changes
    a) resolveOrCreate() line 47 currently defaults gw_port to
       wifidog_port ?: 2060. For MikroTik this must be hotspot_port ?: 80.
       Branch on gateway_type.
    b) gateway_id is NOT NULL in captive_sessions. RouterService::create
       currently leaves gateway_id NULL for MikroTik, so session creation
       fails. Fix both:
         - set network_devices.gateway_id for MikroTik to
           serial_number ?: router_identity ?: 'mt-<id>'
         - in CaptiveSessionService use
           (string) ($gateway->gateway_id ?: $gateway->serial_number ?: $gateway->id)
    c) gatewayAuthRedirectUrl() line 610 currently always builds
       http://{gw_address}:{gw_port}/wifidog/auth?token=...
       Branch:
         if gateway_type === mikrotik:
             return url('/gateway/mikrotik/'.$session->token);
         else:
             existing WiFiDog URL.
       This single branch is what makes PortalPaymentResource,
       toPublicArray(), and the portal's "open gateway" button work for
       MikroTik without touching the frontend.
    d) Do NOT make an HTTP call from gatewayAuthRedirectUrl. It is called by
       API resources; keep it pure. Provisioning happens on the gateway page.
    e) disconnect() stays DB-only for WiFiDog. For app-initiated MikroTik
       removal, call MikroTikService::revoke() from the admin endpoint/job,
       not from the WiFiDog logout path.

6.4 Payment flow
    No change is required to create/pay, because the captive session token is
    already stored in payment metadata and authorizeCaptiveIfPresent() already
    authenticates it. The only change is that gateway_auth_url now points at
    /gateway/mikrotik/{token}.

    Optional improvement (recommended): after markPortalPaid commits, dispatch
      ProvisionMikroTikSession job
    so the router user exists before the browser reaches the gateway page.
    Use DB::afterCommit to avoid calling REST inside the transaction. The
    gateway page still calls ensureProvisioned() as an idempotent fallback.

    Do not let provisioning failure roll back a paid payment. Payment is
    authoritative; provisioning is retriable.

6.5 Provisioning rules
    Username:  wf_<captive token>            (deterministic, unique)
    Password:  random 20-24 chars, stored encrypted on the captive session
    Comment:   wf|<company_id>|<captive_session_id>|<grant expires_at ISO>
    Profile:   wf-<company_id>-<plan_id>     (one per InternetPlan)
    User limits:
      limit-uptime       = remaining grant time (or plan duration)
      limit-bytes-total  = remaining plan data (if data_cap_mb set)
      disabled           = no
    Profile limits:
      rate-limit         = <download Mbps>M/<upload Mbps>M  (verify direction)
      shared-users       = 1
      session-timeout    = 0 (let limit-uptime be the limit)
      idle-timeout       = optional, e.g. 10m to free stale sessions
    If speed fields are null: omit rate-limit (unlimited).
    If data_cap_mb is null: omit limit-bytes-total.
    If duration_unit is UNLIMITED_DATA or duration is null and grant has no
    expiry: omit limit-uptime.

    Idempotency:
      - If session->mikrotik_provisioned_at is set and the access grant is the
        same (store mikrotik_grant_id), return without changing the router.
      - If the user exists with the same name, update it (set) rather than
        adding a duplicate.
      - If a new grant replaces an old one, revoke the old active/user first.
      - Never reset limits on a simple page refresh; that would extend time.

    RouterOS calls:
      GET  /rest/ip/hotspot/user                -> find by name
      POST /rest/ip/hotspot/user/add            -> create
      POST /rest/ip/hotspot/user/set {".id"}    -> update
      GET  /rest/ip/hotspot/user/profile        -> find by name
      POST /rest/ip/hotspot/user/profile/add
      POST /rest/ip/hotspot/user/profile/set {".id"}
      GET  /rest/ip/hotspot/active
      POST /rest/ip/hotspot/active/remove {".id"}
      POST /rest/ip/hotspot/user/remove {".id"}
      POST /rest/ip/hotspot/cookie/remove {".id"}

    Map plan fields:
      speed_download_mbps -> rx rate
      speed_upload_mbps   -> tx rate
      data_cap_mb         -> limit-bytes-total = MB * 1048576
      duration + unit     -> limit-uptime; months => 30 days per month
      devices_allowed     -> shared-users (usually 1 for a MAC-bound session)

6.6 Auto-login page (resources/views/captive/mikrotik-gateway.blade.php)
    Minimal, no JS dependency for the form itself:
      <form id="mt-login" method="post"
            action="http://{{ $gwAddress }}:{{ $gwPort }}/login">
        <input type="hidden" name="username" value="{{ $username }}">
        <input type="hidden" name="password" value="{{ $password }}">
        <input type="hidden" name="dst" value="{{ $dst }}">
        <input type="hidden" name="popup" value="1">
        <button type="submit">Continue to Internet</button>
      </form>
      <script>document.getElementById('mt-login').submit();</script>
    Add a note: "If nothing happens, tap Continue." This covers browsers that
    block mixed-content form posts or disabled JS.
    Mixed content note: the page is HTTPS, the router is HTTP on the LAN.
    Top-level form submissions are normally allowed; test on Android/iOS. If a
    device blocks it, the fallback button/link is the safety net.

6.7 Sync command
    app/Console/Commands/SyncMikroTikRoutersCommand.php
    Schedule: everyMinute() in routes/console.php.
    Options: --router=ID for manual runs.

    For each active MikroTik router (or a queued job per router):
      1. GET /rest/system/resource
         -> update last_seen_at, firmware, status online
         -> if it fails, leave last_seen_at alone; online will go false after
            10 minutes (existing ONLINE_WINDOW_MINUTES)
      2. GET /rest/ip/hotspot/active
         -> for each active entry:
              find CaptiveSession by mikrotik_username or client_mac
              update router_active_id, router_authorized_at, last_seen_at
              find NetworkSession by captive->network_session_id
              update upload_bytes (bytes-in), download_bytes (bytes-out),
                     last_activity_at
         -> for DB active sessions on this router not present in the list:
              mark NetworkSession ended, CaptiveSession disconnected, but only
              after 2 consecutive misses to avoid DHCP/session flaps
      3. Remove expired router users:
         - find users whose comment starts with wf| and whose grant expired
         - remove active entry, then user, then cookie
      4. Never delete a user that still has a usable grant.
    Use a per-router lock (Cache::lock) and a queue to avoid overlapping
    syncs. Do not run this for hundreds of routers in one synchronous command.

6.8 Removal and expiry
    Admin:
      DELETE /api/v1/routers/{router}/clients/{mac}
      -> MikroTikService::removeByMac()
      -> update DB + audit log "router_client_removed"
    Expiry:
      AccessExpiryService::expireGrant() after commit dispatches
      RevokeMikroTikSession job for each affected captive/network session.
      The job calls MikroTikService::revoke().
      The sync job is the backstop if the job fails.
    Revoke steps (order matters):
      1. remove /ip hotspot active entries for the MAC
      2. remove /ip hotspot user by name
      3. remove /ip hotspot cookie for the MAC
      4. update DB (NetworkSession ended, CaptiveSession disconnected/expired)
    Idempotency:
      - If the active entry is already gone, continue to user/cookie removal.
      - If the user is already gone, treat as success.
      - Do not fail the whole operation on a single 404; collect results and
        log.

8. PLAN -> ROUTEROS MAPPING (WORKED EXAMPLE)
------------------------------------------------------------------------------
Plan:
  name = "1 Hour 10Mbps"
  duration = 1, duration_unit = HOURS
  price = 1000
  speed_download_mbps = 10
  speed_upload_mbps = 5
  data_cap_mb = 500
  devices_allowed = 1

Grant created at 10:00, expires at 11:00. User opens gateway page at 10:07.

  Profile:
    /ip hotspot user profile add name=wf-7-12 rate-limit=10M/5M \
        shared-users=1 session-timeout=0
  User:
    /ip hotspot user add name=wf_<token> password=<random> profile=wf-7-12 \
        limit-uptime=53m limit-bytes-total=524288000 \
        comment="wf|7|345|2026-11-02T11:00:00Z"

  Remaining time is used, not the full hour, so re-provisioning/refresh does
  not extend the purchase. Remaining data uses data_limit - data_used when
  those are tracked; otherwise plan data_cap_mb.

  If the plan has no speed: omit rate-limit.
  If the plan has no data cap: omit limit-bytes-total.
  If the plan is unlimited: omit limit-uptime (grant expiry may still apply).

  Note on rate-limit direction: RouterOS hotspot profile rate-limit is written
  as rx/tx. Confirm on the lab router which direction is download; if it is
  reversed, swap the mapping once in the mapper, not per plan.

9. CALLBACKS AND ACCOUNTING IN DETAIL
------------------------------------------------------------------------------
9.1 Backend polling (baseline, always on)
    /rest/ip/hotspot/active gives, per client:
      .id, user, address, mac-address, uptime, bytes-in, bytes-out,
      server, login-by
    Map:
      upload_bytes   = bytes-in   (client -> network)
      download_bytes = bytes-out  (network -> client)
    This matches the WiFiDog counter mapping in WiFiDogService::recordCounters.

9.2 Router on-logout callback (optional, faster logout)
    Create a script and call it from the hotspot profile. Test variable
    availability on your RouterOS version before relying on it.

    /system script add name=waifai-logout source={
      /tool fetch url="https://BACKEND/api/mikrotik/callback?router=ROUTER_ID&secret=SECRET&event=logout&user=\$user&address=\$address" \
          keep-result=no
    }
    /ip hotspot profile set [find name=<profile>] \
        on-logout="/system script run waifai-logout"

    Usage (bytes-in/bytes-out/uptime) is taken from the polling sync; the
    callback is only for fast session-state changes. This avoids relying on
    hyphenated hotspot variables (e.g. $bytes-in) whose exact syntax varies
    between RouterOS versions. Test $user/$address scoping on your firmware,
    and do not make correctness depend on the callback; polling reconciles.

9.3 Router on-login callback (optional)
    Same pattern with event=login. It lets the backend mark
    router_authorized_at immediately instead of waiting for the next poll.
    Again, polling is the source of truth.

9.4 Callback security
    - HTTPS only.
    - Per-router callback_secret, compared with hash_equals.
    - Throttle and validate router id.
    - Never include API credentials in the callback.
    - If the secret is in the URL, it can appear in router logs; rotate it if
      that is a concern, or use http-header-field if your RouterOS version
      supports it.

9.5 Payment callbacks (unchanged)
    These remain exactly as today:
      POST /api/v1/webhooks/payments/{provider}
      POST /api/v1/webhooks/payouts/{provider}
      POST /api/v1/webhooks/platform-payments (legacy)
    They mark PlatformPayment paid, which marks the PaymentTransaction paid,
    which authenticates the captive session. MikroTik provisioning happens
    later when the gateway page is opened (or via the optional job).

10.3 Service skeleton

  namespace App\Services\MikroTik;

  use App\Models\CaptiveSession;
  use App\Models\InternetPlan;
  use App\Models\NetworkDevice;
  use Illuminate\Support\Facades\Crypt;
  use Illuminate\Support\Facades\Http;

  class MikroTikService
  {
      public function test(NetworkDevice $router): array
      {
          $start = microtime(true);
          $resource = $this->get($router, '/system/resource');
          $active = $this->get($router, '/ip/hotspot/active');

          return [
              'reachable' => true,
              'authenticated' => true,
              'routeros_version' => $resource['version'] ?? null,
              'uptime' => $resource['uptime'] ?? null,
              'active_clients' => is_array($active) ? count($active) : 0,
              'hotspot_enabled' => true,
              'latency_ms' => (int) round((microtime(true) - $start) * 1000),
              'message' => 'RouterOS REST API is reachable and authenticated.',
          ];
      }

      public function ensureProvisioned(CaptiveSession $session): void
      {
          // 1. guards: mikrotik router, authenticated, usable grant
          // 2. idempotency: same grant + provisioned_at -> return
          // 3. ensureProfile($router, $grant->internetPlan)
          // 4. find/create/update hotspot user
          // 5. persist username/password(encrypted)/user id/provisioned_at
      }

      public function revoke(CaptiveSession $session): void
      {
          // remove active by MAC, remove user by name, remove cookie
      }

      private function get(NetworkDevice $router, string $path): array
      {
          $response = $this->client($router)->get($path);
          if ($response->failed()) {
              throw new MikroTikException('RouterOS rejected GET '.$path, [...]);
          }
          return $response->json() ?? [];
      }

      private function client(NetworkDevice $router)
      {
          $scheme = ((int) $router->api_port === 80) ? 'http' : 'https';
          $request = Http::baseUrl($scheme.'://'.$router->api_host.':'.$router->api_port.'/rest')
              ->withBasicAuth($router->api_username, Crypt::decryptString($router->api_password))
              ->acceptJson()
              ->timeout(10);

          return $router->api_verify_tls ? $request : $request->withoutVerifying();
      }
  }

11. ERROR HANDLING AND EDGE CASES
------------------------------------------------------------------------------
11.1 Router unreachable during provisioning
    - Payment is already recorded; do not fail the payment.
    - Gateway page shows "We could not reach the router. Retry" with a
      button that reloads the page.
    - The optional ProvisionMikroTikSession job retries with backoff.
    - The sync job will eventually provision if the grant is still usable.

11.2 User closes browser after paying
    - Nothing is provisioned until the gateway page is opened, which is fine.
    - On reconnect, login.html creates/reuses a pending session for the same
      MAC; findReusableSession finds the authenticated session; the portal
      resumes and the gateway page provisions then.
    - This is why the captive session must stay authenticated until grant
      expiry, and why MAC normalization must be consistent.

11.3 User pays but connects a different device
    - The token is tied to the original MAC. The new device gets a new
      pending session and is not authorized. This is intended. If the plan
      allows multiple devices, that requires a separate design (shared grant
      tokens or multiple sessions). Do not silently allow it.

11.4 Duplicate provisioning / page refresh
    - Use deterministic username + provisioned_at + grant id.
    - Do not reset limit-uptime on every page load.
    - If the user is already in /ip hotspot active, redirect to the original
      URL instead of submitting the login form again.

11.5 Already logged in on the router
    - Check active list before rendering the form. If the MAC is active and
      the grant is usable, show "You are already online" and redirect.
    - If active with a different user/grant, revoke and provision the new one
      only when the grant differs.

11.6 Router reboot / config loss
    - RouterOS hotspot users are stored in the router config; a config reset
      loses them. The sync job can re-provision active grants on demand, but
      it cannot know the password unless it is stored (it is, encrypted).
    - The setup guide should include backup/restore of the router config.

11.7 Router clock skew
    - RouterOS limits use its own uptime, not wall clock, so limit-uptime is
      safe. But TLS and log correlation need NTP. Configure NTP.

11.8 Multiple companies per router
    - This plan assumes one company per router (the login template has one
      subdomain). If you need multi-tenant routers, the login page must ask
      for/derive the company and the portal key must map to a company. Do not
      guess; make it explicit in the router record.

11.9 MikroTik v6
    - No REST API. You would need the legacy API (8728/8729) or SSH, plus a
      different client. Do not claim v6 support unless you build and test it.

11.10 Payment provider redirect pages
    - If the provider sends the browser to an external checkout domain, add
      that domain to the walled garden before go-live. Test the exact flow on
      a real phone.

17. OPEN DECISIONS (ANSWER BEFORE CODING)
------------------------------------------------------------------------------
1. Connectivity: public REST + IP allowlist, or WireGuard/VPN?
   This determines whether api_host may be private and how setup is written.
2. Do you need RADIUS now, or is REST + one-time user enough for phase 1?
   Recommend REST first; RADIUS when router count/accounting demands it.
3. Do you need MikroTik v6 support? If yes, add the legacy API/SSH client;
   the REST plan does not work on v6.
4. Which payment methods must work through the browser (checkout redirect)
   and therefore need walled-garden entries?
5. Should a paid grant be single-device (token/MAC bound) or multi-device?
   The current model is single-device; changing it affects provisioning.
6. How long should router users be retained after expiry? Remove immediately
   (recommended) or keep for reconnect/audit?
7. Do you want router-initiated callbacks (on-logout) or is 1-minute polling
   acceptable? Polling is the baseline; callbacks are an optimization.
8. Which timezone/clock source for grant expiry comparisons? The backend
   uses app timezone; RouterOS limits use uptime, so this is mostly a display
   and log-correlation concern.

18. OPTION B - RADIUS (WHEN YOU OUTGROW OPTION A)
------------------------------------------------------------------------------
If you want MikroTik to behave even more like Ruijie (server-driven auth,
real accounting, centralized revocation), use RADIUS:

  Router:
    /radius add service=hotspot address=<radius-host> secret=<shared> \
        timeout=3s
    /ip hotspot profile set [find name=<profile>] use-radius=yes
    # accounting and authentication both go to RADIUS

  Backend:
    - Run FreeRADIUS with a SQL backend (MariaDB/MySQL).
    - On payment/voucher, write:
        radcheck: username, Cleartext-Password
        radreply: Session-Timeout, Idle-Timeout, Mikrotik-Rate-Limit,
                  WISPr-Bandwidth-Max-Down/Up, Acct-Interim-Interval
        radusergroup (optional)
    - On expiry/removal, delete the user and optionally send a RADIUS
      Disconnect-Message (CoA) to the router; or use RouterOS REST to remove
      the active session.
    - radacct gives accounting (Start/Interim/Stop), so you do not need to
      poll /ip hotspot active for usage.

  Browser:
    - login.html still redirects to the backend portal.
    - After payment, the auto-login page posts the RADIUS username/password
      to the router, exactly like Option A. The router asks RADIUS instead of
      checking a local user.

  Pros:
    - Standard, scalable, real accounting, immediate disconnect messages.
    - No per-router hotspot user CRUD.
  Cons:
    - New RADIUS server + DB + network path + monitoring.
    - More moving parts than Option A.
    - Still needs a login page redirect and an auto-login step for the
      seamless UX (unless you use MAC-based auth, which has its own issues).

  Recommendation: implement Option A now; keep the provisioning interface
  small enough that Option B can replace the `MikroTikService` internals later
  without changing the portal/payment code.

    - POST /api/mikrotik/callback         optional on-login/on-logout/accounting.

      usage, stale sessions, and removes users whose grant is no longer usable.

      ProvisionMikroTikSession after commit. Both are best-effort; the gateway
      page and sync command are the retry paths.
