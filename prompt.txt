The AP is configured with portal URL https://waifai.shereheyangu.com/public/api/wifidog/portal?.... This route 302-redirects to http://www.google.com instead of the captive portal, causing a redirect loop (AP intercepts the Google request again since the client is still unauthorized → "too many redirects").

Fix: /public/api/wifidog/portal (the alias used by the AP) must behave exactly like /api/wifidog/login — resolve the gateway by gw_id, create/return the captive session, and 302 to:
https://waifai.cloud.shereheyangu.com/connect?subdomain={slug}&session={64-char-token} (+ forward mac, ip, gw_address, gw_port if available).

Redirect to Google (or the original url param) only when the captive session is already authenticated — never on a fresh denied client.
Once the backend redirects the denied client to the /connect page (instead of Google), the loop disappears: portal loads → customer pays → frontend navigates to http://{gw_address}:2060/wifidog/auth?token=... → AP returns Auth: 1 → internet.
